GET /api/v1/contests/403/leaderboard performance comparison

Measured on 2026-11-18 against the existing deterministic seed_perf.py contest (seed 20261118; 200 registered participants, 3 contest problems, 5,000 submissions with authoritative attempts and verdicts). The seed command was run before both measurements and reused contest_id 403 with the same row counts. The HTTP benchmark used 10 concurrent clients, 20 requests each (200 GETs total), authenticated requests, default limit 50, and reported client-observed request latency. Each p50/p95 is one measured run; no statistical confidence interval is claimed.

Before targeted change (existing index without authoritative_attempt_id):
- HTTP p50: 170.598 ms; p95: 286.068 ms; 200 requests; 0 errors.
- EXPLAIN ANALYZE total: 90.2 ms (51 rows returned in the default page).
- Submission access used ix_submissions_participant_problem_submitted, with base-row access to test/read authoritative_attempt_id.

After targeted change (same index extended to cover authoritative_attempt_id):
- HTTP p50: 232.382 ms; p95: 401.561 ms; 200 requests; 0 errors.
- EXPLAIN ANALYZE total: 72.0 ms (51 rows returned in the default page).
- EXPLAIN shows “Covering index lookup on submissions using ix_submissions_participant_problem_submitted” in both accepted-solve and wrong-count access paths.

Observed result: EXPLAIN ANALYZE was 18.2 ms lower in this run, while HTTP p50/p95 were higher. These measurements do not establish an end-to-end latency improvement. The index is retained because the plan confirms covering reads and lower analyzed SQL time; endpoint-level benefit remains unproven. Both plans have materialized temporary results, window-order sorting, and final leaderboard sorting; neither shows a base-table full scan of submissions.

Targeted schema change: Alembic 0005 replaces ix_submissions_participant_problem_submitted with the same index plus authoritative_attempt_id as its final column. Leaderboard SQL and API behavior were not changed.


Rejected index experiment (measured separately, then reverted):
- Candidate index: verdicts(judge_attempt_id, verdict), named ix_verdict_attempt_cover.
- The captured plan continued to report “Single-row index lookup on verdicts using uq_verdict_attempt (judge_attempt_id=submissions.authoritative_attempt_id)” rather than the candidate index.
- One 200-request HTTP run measured p50 171.755 ms and p95 456.268 ms, with 0 errors.
- This candidate was not retained. It was replaced by the submission covering-index change documented above.
